## Ephemeris 0.12.2

A fix for routers with more than one worker, and limits on sessions. The
card's RSS table is spread over every worker's queue again, so extra
workers get traffic. "auto" session tables are capped at a realistic size,
one host can't fill the table for everyone else, and the NAT port search
is bounded. The end-to-end test now runs two workers on cards that spread
traffic as real hardware does.

### Fixed: workers left without traffic

At every start, the router sets each data-plane card to one RX queue per
worker. It then set the card's RSS hash (`ethtool -X <dev> hfunc
toeplitz`), which also marks the card's queue table as configured. After a
later start with more workers, that table could stay as it was. Everything
then arrived on the first queue: one worker did all the work while the
others sat idle. Some drivers also refuse to change the number of queues
while the table is configured.
- At every start, the table now goes back to the driver's default first.
  Then the queue count is set, and the table is spread evenly over all the
  workers' queues (`ethtool -X <dev> equal <workers>`, Toeplitz, symmetric
  where the card can).
- The router warns at start if a card's table still sends nothing to some
  worker's queue, with the command that fixes it:
  `<dev>: the card's RSS table sends nothing to queue(s) [1], so those
  workers get no traffic from it. Fix: ethtool -X <dev> equal 2`.

### Sessions: realistic limits

**"auto" caps at 2 million sessions for the whole router.**
`sessions.max_per_worker = "auto"` used to give the session tables half
of the free memory, up to 16 million sessions *per worker*. A machine with
16 GB could reserve close to 5 GB for them.
- It still takes half of what's free, but now at most 2 million sessions
  in all (about 600 MB of tables), split between the workers. It never
  goes below 16,384 per worker.
- That's more than a branch or a busy office ever has open. A bigger table
  only makes lookups slower and lets a flood of junk flows linger.
- A number still overrides it, up to 16 million per worker.

**A limit per host: `sessions.max_per_host`** (default 50,000; 0 turns it
off). One address may have at most this many sessions open at once.
- A busy PC uses a few hundred and a torrent client a few thousand, so
  only a scan, malware or a runaway program gets there. Its new flows are
  refused as `host-session-limit`; its existing flows, and everyone else's,
  carry on. Carrier-grade NATs must offer the same (RFC 6888, REQ-4).
- Sessions count against the address that started them, so replies and
  the server's side don't count.
- Each worker enforces its share (the limit divided by the workers), as a
  host's flows spread evenly over them.
- The counting space is reserved at start, for up to 65,536 addresses per
  worker, so nothing is allocated per packet. Beyond that, a new address
  isn't counted (and so not limited).
- On the portal: "Sessions per host" under Sessions.

**A bounded NAT port search.** Picking a NAT port whose replies come back
to the right worker now stops after 8,192 of that worker's own ports
(`nat-exhausted`), as the plain split already did. Before, when one
destination was nearly out of ports, every new flow to it could check all
64,512.

### Testing
- **Two workers in the end-to-end test.** The test router's two data-plane
  cards each have two queues, spread by Toeplitz RSS as real hardware does
  (QEMU's virtio-net RSS). A new phase switches to two workers and checks:
  - each card has a queue per worker;
  - the outside card's RSS is read, with TCP and UDP hashed on ports;
  - 64 UDP flows through NAT, each from its own port, are all answered;
  - 8 TCP streams work;
  - both queues of both cards carry traffic, and no worker is left without
    a queue;
  - under 1% of packets are handed between workers, and no reply is lost
    (`nat-wrong-worker` and `nat-no-session` stay at zero);
  - pings work. ICMP is spread by address only, so it is handed over as
    needed.

  Then it goes back to one worker.
- New unit tests: the per-host limit (in the session table and through the
  pipeline), the auto cap and its split between workers.

### When upgrading
- **Routers with more than one worker:** the queue table is spread again
  the first time the router starts on 0.12.2. Afterwards, check the startup
  log for `sends nothing to queue`. If it's there, the card refused the
  change: run the `ethtool` command it gives, then `ephctl restart`.
- **Less memory reserved under "auto"** on machines with a lot of it. If
  you need more than 2 million sessions, set `max_per_worker` to a number.
- **The per-host limit is on by default.** A host that really keeps more
  than 50,000 sessions open (a proxy, a NAT or a server farm behind this
  router) needs a higher `max_per_host`, or 0. Watch for
  `host-session-limit` drops.
