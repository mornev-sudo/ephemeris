## Ephemeris 0.14.0

A controller can now do more than push configs: check for and install
updates, reboot or restart the router, and read its live tables. And this
release carries the fixes from a security review of the whole code base,
among them one that matters to every router getting its address by DHCP:
**please update**.

### Security

Found in a review of the whole repository and fixed here, each with a test.

- **A packet that could stop the router.** A DHCP packet with its UDP
  header cut short was read past its end, which stops ephemerisd. Anyone
  on a link where the router serves or requests DHCP could send one: on a
  WAN with `address = "dhcp"`, that's anyone on the ISP's side of it. Such
  packets are now refused. Every release since 0.6.0 (which brought DHCP)
  is affected.
- **A controller could take over the admin password.** A pushed config
  could point `[management] token_file` at a file whose contents the
  controller knows, and so learn the API token, which may set a new admin
  (and root) password. A push now keeps the router's own `token_file`,
  the admin password's hash stays next to the config wherever the token
  file is, and a token file holding fewer than 32 characters is refused
  rather than used. Only enrolled routers (0.13.0) were affected.
- **A DHCP server or PPPoE peer could take over inside routes.** A lease,
  a server route (option 121/249) or a PPPoE session could add routes
  inside networks configured on the router (a LAN, a static route's
  gateway, another SD-WAN site), sending that traffic out of the WAN, in
  plain text. The router now ignores anything handed out that lands
  inside an interface's subnet, another site's prefixes or an overlay
  route, and server routes into a static route too; what's ignored shows
  in the WAN status (see below). A WAN subnet broader than the LAN, and a
  double NAT inside a broad static route, still work.
- **SD-WAN: a nonce could repeat at a rekey.** When another worker
  confirmed the new session at just the wrong moment, a packet was sealed
  with the new session's key under the old one's packet number, so that
  number came round again under the same key. Each packet is now sealed
  with exactly the session it was numbered for.
- **Smaller fixes in the data path:**
  - "Packet too big" errors from a hub that NATs its spokes' internet
    traffic quoted the packet as translated, giving away the spoke host's
    private address (and the server couldn't match it, so path MTU
    discovery didn't work through such a hub). They now quote the packet
    as the server sent it.
  - An ICMP error from inside about a packet no session knows, which would
    need NAT to leave, left with the inside host's address. It's dropped
    (`nat-untranslatable`).
  - After a route change, the first packet of a session could arrive on
    any port and be accepted. It must now come from where that direction
    came before, or from where the new routes lead back to its sender.
  - ARP replies went to whatever MAC address a request named (broadcast
    too) and carried whatever the request carried after the ARP message.
    They now go only to a host's own address, padded with zeros.
- **Hardening:** `ephctl config edit` writes its temporary copy (which
  holds secrets) as a new file readable only by its user; the bounds check
  on packet buffers can't overflow; `nic-setup` reads the config through
  `ephemerisd --nic-setup` (as TOML) rather than line by line, so a
  `device =` line inside a string is just text.

### Stricter by default

- **Source check on inside interfaces.** A packet arriving on an inside
  interface must come from an address that routes back out of it (strict
  reverse path, RFC 3704). Before, only the other interfaces' own subnets
  were refused, so a LAN host could pass for a network behind another port,
  or for an internet address, for example to match `management_from`.
  Where traffic comes back another way than it left (asymmetric routing),
  set `strict_source = false` on that interface (or "Source check: loose"
  in the portal). Outside interfaces keep the subnet check only: several
  WANs and SD-WAN tethers may use any of them.
- **ICMP sessions.** A ping session carries requests one way and replies
  the other: the far end can no longer ping the inside host through it, and
  an echo reply nobody asked for starts nothing. Other ICMP that isn't an
  error (redirects, timestamps, address masks) gets no session: it's
  forwarded only from interfaces that may start sessions, and not when it
  would need NAT. Parameter Problem is handled like the other ICMP errors.

### Managed by a controller

- **Operations** (capability `operations`): `overlay.identity`,
  `system.update.check`, `system.update`, `system.reboot` (now, or `at` a
  time within a week, as a one-off systemd timer) and `restart`. Each is in
  the router's audit log as the controller's. `update.progress` now reports
  `installing`, `installed` and `failed` (with the reason).
- **Live tables** (capability `tables`): `sessions.get`, `routes.get` and
  `neighbors.get` as `{items, total}` with `limit` up to 1000;
  `dhcp.get`, `wan.get` and `overlay.get` as the API's own answers.
- **The router's host name** in `hello` comes from the kernel (the image
  sets it from the `system.hostname` credential and never writes
  `/etc/hostname`); the SD-WAN directory entry and the DHCP client use it
  too.
- [The contract](https://github.com/mornev-sudo/ephemeris/blob/v0.14.0/docs/controller-api.md)
  documents the operations and their answers and is no longer a draft.

### Updates from your own mirror

- **`[system] update_url`**: where updates come from, instead of GitHub (a
  mirror, or a controller): a plain `http(s)://` directory URL. It's
  preferred over the `ephemeris.update_url` credential given at
  deployment, and checked before every update check and install. Updates
  are still only installed if signed by the release key, whatever the
  source.

### WAN status

- What the router ignored from a lease or PPPoE session shows for as long
  as it holds: `ignored` in `GET /wan`, `IGNORED: …` in `ephctl wan`,
  "ignored" on the dashboard. It's logged once when it first appears.

### When upgrading

- **Asymmetric routing on an inside interface** (traffic returning on
  another interface than it left by) now needs `strict_source = false`
  there, or those packets are dropped as `spoofed-source`.
- **A hand-set API token shorter than 32 characters** is refused: token
  authentication stays off (portal logins still work) until the token file
  holds a longer one, or is deleted so the router makes a new one.
- **A lease or PPPoE session inside a configured network** is ignored
  where it used to be applied: check `ephctl wan` if an interface stays
  without an address.
- **Non-echo ICMP** (timestamps, address masks, redirects) through the
  router no longer opens a way back for replies.
- **A controller's push** can't change `[management] token_file`; it can
  still change the rest of `[management]`.
