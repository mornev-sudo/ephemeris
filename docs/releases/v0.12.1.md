## Ephemeris 0.12.1

An SD-WAN and multi-core release. Tethers can get fresh session keys from
a handshake (forward secrecy), using AES-256-GCM where both routers have
it in hardware. Spokes with several dynamic WAN links work, and so do hubs
whose PPPoE address changes. NAT replies now reach the worker that made
the translation, so NAT can grow with the number of cores. Sessions that
never get an answer can be diagnosed, and every session timeout can be
configured.

(0.12.0 was skipped.)

### SD-WAN

**Session keys from a handshake.** A `[[site]]` entry with the other
router's `public_key` gets new session keys every two minutes from a
Noise IKpsk2 handshake, the pattern WireGuard uses. A key stolen later
decrypts nothing recorded earlier. The site's pre-shared `key`, if set,
is mixed into the handshake. Sites without a `public_key` keep using
their pre-shared key as before, so you can move pairs over one at a
time.
- Each router has its own X25519 key pair, kept in
  `/var/lib/ephemeris/overlay-identity` and made on first use. See it with
  `ephctl sdwan identity`, `ephemerisd --sdwan-identity` or the portal.
  Set a site's key with `ephctl sdwan public-key`. `ephctl sdwan entry
  <site>` prints the entry the other router needs for this one.
- No packets are lost when keys change: up to three sessions per site
  stay valid. A responder only uses new keys once a packet sealed with
  them has arrived.
- The handshake retries over the next WAN when one doesn't answer, and
  starts again after 3 s with nothing from the peer. When both routers
  start one at once, the site id breaks the tie. Junk is rejected cheaply
  (mac1). Answered initiations are limited to 5 a second per site, and
  handshake messages to 20 a second per worker.
- A peer without a fixed address is learned from its handshake.

**AES-256-GCM or ChaCha20-Poly1305.** The cipher for session keys is
agreed inside the handshake, so it can't be downgraded in transit.
- `[overlay] cipher = "auto"` (the default) picks AES-256-GCM when both
  routers have AES in hardware (AES-NI and PCLMULQDQ on x86, the AES and
  PMULL instructions on ARM), and ChaCha20-Poly1305 otherwise.
  `"aes-256-gcm"` or `"chacha20-poly1305"` forces one. A router that
  can't use the forced cipher gets no keys, and the log says why.
- On CPUs with AES-NI (Intel Atom C3000 and newer included), AES-GCM uses
  much less CPU per packet. On a development machine: about 0.47 µs for
  a 1440-byte packet, against about 3.2 µs for ChaCha20.
  `ephemerisd --bench-crypto` measures both on your own router.
- The cipher in use shows in `ephctl sdwan sites` and on the portal's
  SD-WAN page.
- Pre-shared-key tethers stay ChaCha20-Poly1305.

**Addresses that change**
- **Spokes with several dynamic links.** `links = N` on a `[[site]]`
  without addresses: the hub keeps one tether per link of that site on
  each of its WANs. Once its first packet authenticates, each tether
  follows one of the spoke's links: its address, its NAT port, and their
  changes. A tether silent for 30 s can be taken over by another link. A
  link with no tether left to take it is counted as `overlay-links-full`.
  The portal's "Copy entry" fills in `links`.
- **Hubs whose address changes** (a PPPoE redial). Every tether follows
  its peer to a new address, configured or not, but only on packets that
  authenticate and aren't replays. For an hour after a router's outside
  address changes, it announces old → new to every peer once a second
  (sealed). Tethers still sending to the old address move. This also
  covers spokes behind NATs that drop packets from unknown addresses, as
  long as one path still works.
- Peers that moved are saved (`overlay-moved` in the state directory) and
  restored after a restart, unless you have changed their configured
  address since.
- Hardening: handshake messages no longer move a tether. A replayed
  initiation still verifies, so its answer goes back to where it came
  from, and the tether stays where it was.

**Fixed: a busy fast link took the slow one down.** A sending worker
numbers its packets with one counter for all its tethers. The receiver
kept a single replay window (1024 packets) per sender, shared by all of
them. While fibre carried a gigabit, LTE's packets arrived more than a
window behind fibre's and were dropped as replays: LTE probes went
unanswered, LTE was marked down, and classes that prefer it moved to
fibre. Each sending tether now has its own window. The tether id is in
the authenticated header, so a packet replayed onto another path is
still refused.

### Many cores: NAT that scales

A network card spreads incoming packets across its queues by hashing
their addresses and ports (RSS). Each worker handles one queue. Before,
a reply could arrive on a different worker than the one holding its NAT
session, and was dropped.
- **Ports chosen by the card's hash.** At startup the router reads each
  card's RSS key and queue table, and asks outside cards to hash TCP and
  UDP on ports as well as addresses. Each worker then picks NAT ports
  whose replies the card will deliver back to that same worker. Nothing
  is shared between workers, so NAT throughput can grow with the number
  of cores. The client's own port is kept whenever its reply would land
  on the right worker anyway.
- **Hand-off as a safety net.** A packet that still lands on the wrong
  worker is copied to the right one through a bounded queue, which wakes
  that worker straight away. That covers:
  - ICMP, which cards hash on addresses only;
  - ICMP errors about a translated packet;
  - PPPoE WANs;
  - cards that won't report their RSS settings;
  - a card that hashes differently from what the router expects.

  A packet is handed on at most once.
- **SD-WAN too:** a packet coming out of a tether is handed to the worker
  that its LAN-side replies will reach.
- New counters: `handed-off` (packets passed to another worker),
  `handoff-full` (dropped because that worker's queue was full), and
  "handed between workers" in the API.
- The startup log says what each card reported, for example
  `ens1f0: Toeplitz RSS over 128 entries; ports hashed: TCP yes, UDP yes`,
  or why the router falls back to hand-off.
- Limit: a PPPoE WAN still arrives on one queue. Replies reach the right
  worker, but that queue's worker does the PPPoE work for all of them.

### Sessions

**Diagnosing flows that get no reply**
- New drop reasons: `nat-no-session` (a reply to a NAT port that has no
  session) and `nat-wrong-worker` (a reply that reached a worker that
  doesn't own its port). Both used to count as `local-unhandled`.
- Sessions that expire without a single packet back are counted, in
  `ephctl status` and on the dashboard. With session tracing on, each one
  is logged with what was sent and how it was translated.

**Timeouts**
- Every protocol and state has its own timeout. New settings:
  `tcp_handshake_timeout_secs`, `tcp_closing_timeout_secs`,
  `tcp_closed_timeout_secs` and `other_timeout_secs` (GRE, ESP and the
  like).
- **New defaults**, from the NAT RFCs: TCP established 2 h 4 min
  (RFC 5382, was 1 h) and ICMP 60 s (RFC 5508, was 30 s). Unanswered UDP
  and TCP handshakes stay at 30 s. The longest idle timeout you can set
  went up from an hour to a day.
- **Per-application timeouts**: `[[sessions.timeout]]` entries, matched
  by protocol and server port (first match wins), with `idle_secs` and
  `unanswered_secs`. They can also be edited in a table on the portal.
- **`early_drop = true`** (the default): when the session table is full,
  the unanswered session closest to expiring is dropped to make room,
  instead of the new connection being refused.

**Fixes**
- A timer wheel that went unchecked for more than one full turn could
  keep a live session past its timeout.
- A UDP checksum that comes out as zero after NAT is now sent as 0xffff.
  Zero means "no checksum" (RFC 768).

### Testing and CI
- **SD-WAN lab in CI**: `lab/netns/sdwan-test.sh` runs two routers with
  public keys over a fibre-like WAN (5 ms each way) and an LTE-like one
  (40 ms each way). It checks:
  - the handshake;
  - path choice per class;
  - Frag Needed at the overlay MTU;
  - TCP throughput over each tether;
  - failover when the fibre is cut, and recovery.

  Its routers are built with a new optimised `lab` profile (release
  without whole-program LTO, so it builds quickly). Throughput is reported
  without TCP's slow start, with retransmissions, and netem's queue is deep
  enough for the 80 ms path. The summary table waits until the cut has
  left the loss window.
- New tests:
  - session keys and the handshake;
  - the cipher choice (every combination, plus a check that the two
    ciphers never open each other's packets);
  - links and address changes;
  - steering with four workers;
  - the Toeplitz hash, against Microsoft's published vectors;
  - per-tether replay windows.

  The fuzzing router now includes a site with session keys (AES).
- **Quieter CI.** Dependabot checks monthly, opens at most three pull
  requests per ecosystem, and no longer rebases them whenever `main`
  changes. Security updates still come as soon as an advisory is
  published. A new push to a pull request cancels that PR's run still in
  progress. Builds of `main` are never cancelled.

### When upgrading
- **SD-WAN keeps working as configured.** Tethers without `public_key`
  use their pre-shared key as before, and a 0.11.0 router can still talk
  to a 0.12.1 one over them. A 0.11.0 router counts the newer one's
  address announcements as `bad-overlay` drops; that's harmless. To
  switch a pair to session keys, upgrade both routers, then put each
  router's public key in the other's `[[site]]` entry.
- **Longer TCP and ICMP timeouts.** Established TCP sessions stay up to
  2 h 4 min idle instead of 1 h, so the table can hold more idle
  sessions. If you had set `tcp_established_timeout_secs` or
  `icmp_timeout_secs`, your values still apply.
- **Outside cards are set to hash UDP on ports** when the router runs
  more than one worker (`ethtool -N <dev> rx-flow-hash udp4 sdfn`; most
  cards already do this for TCP). The setting lasts until the card is
  reset or the machine reboots, and the router sets it again at every
  start.
- **New drop reasons** (`nat-no-session`, `nat-wrong-worker`,
  `handed-off`, `handoff-full`, `overlay-no-key`, `overlay-handshake`,
  `overlay-links-full`) appear in the API and in `ephctl`. Anything that
  matched on `local-unhandled` for NAT replies should look at the new
  names.
