## Ephemeris 0.13.0

Routers can now be managed by a controller: one place from which an
organisation runs all its routers. A router enrols once, connects out to
its controller over TLS, reports its state, and takes config pushes that
undo themselves unless confirmed, so a bad push can't strand a remote
router. Nothing changes for a router that isn't enrolled.

The router's side of the contract is documented in
[docs/controller-api.md](https://github.com/mornev-sudo/ephemeris/blob/v0.13.0/docs/controller-api.md),
so any controller that speaks it can manage Ephemeris routers.

### Managed by a controller

**Identity.** Each router has a management key pair (Ed25519), made on
first start and kept in `/var/lib/ephemeris/controller-identity`. It's
separate from the SD-WAN key. Its public key is the router's id towards a
controller:
- `ephctl controller identity`, `ephemerisd --controller-identity` and
  the portal show it;
- the console's login prompt and the portal show its first 32 hex
  characters in groups of four, the way the controller shows it too, so
  people can compare them.

**Enrolling.** A controller's administrator creates an enrolment string,
`eph-enrol:v1:<url>#<token>@<fingerprint>`. The router can be given it:
- with `ephctl controller enrol <string>`;
- in the portal: System → Controller;
- at deployment, with no one logging in (zero-touch): as the
  `ephemeris.controller` credential (VM SMBIOS strings, e.g.
  `ENROL=... lab/proxmox/deploy-image.sh`), or as the file
  `/var/lib/ephemeris/enrolment` (for installers and VMs that can't pass
  credentials; removed once used).

Zero-touch enrolment retries while the controller can't be reached (the
WAN may not be up yet), stops on a refused token, and never tries a spent
token again. A successful enrolment commits a `[controller]` section,
which portal edits and controller pushes leave alone.

**Claim tokens.** A controller may hand out one reusable string per
organisation or site, so every router can carry the same one (an image, an
installer, a VM template). A router enrolled with it waits, showing
"waiting for approval", until an administrator approves it after comparing
its key with the router's console.

**The connection.**
- The router connects out: no open ports, works behind NAT, and through
  the data plane with `[management] outbound = "dataplane"`.
- TLS 1.3 only. The controller is trusted by the key pinned at enrolment,
  not by certificate authorities; the router presents a certificate for
  its management key.
- A WebSocket with pings every 30 s, closed after 90 s of silence, and
  reconnected with backoff (1 s to 5 min, with jitter).
- `ephctl controller status`, the portal and the console's login prompt
  show where the link stands: not managed, enrolling, connecting,
  connected, waiting for approval, not enrolled, or the last error.

**Telemetry.** A connected router sends:
- `status` (what `GET /status` returns): every 30 s, and when an
  interface, address, WAN lease, PPPoE session or tether changes;
- `stats`: the samples it holds right after connecting (up to the last
  hour), then every 5 minutes;
- events: tethers up or down, path changes, WAN leases and PPPoE sessions
  gained or lost, commits and rollbacks, a config that failed at start,
  and an update starting. Repeats within 10 s are coalesced, at most 60 go
  out a minute, and `ephctl controller status` counts any not sent.

**Config from the controller.**
- `config.push`: a complete config, made from the running one. Refused if
  the router's config changed since or another push waits for its
  confirmation; checked exactly as a portal commit; then committed as a
  confirmed commit and applied live, or with a restart if the push asks.
- The controller confirms once the router is back and healthy; without
  that, the router goes back by itself.
- `config.get` and `config.history`; and the router tells the controller
  within a second of any change the controller didn't make (drift).
- Pushes and confirmations are in the router's audit log as the
  controller's.

### Config changes for everyone

- **A config version number** that counts every change of the running
  config, commits and rollbacks alike, and survives restarts
  (`/var/lib/ephemeris/config-version`).
- **Confirmed commits survive a restart.** The deadline is saved
  (`/var/lib/ephemeris/pending-confirm.json`): a commit still waiting
  after a restart keeps its deadline, and one whose deadline passed while
  the router was down is rolled back as the router starts, before the
  unconfirmed config runs.
- **An unconfirmed commit that needed a restart is now undone by
  restarting.** Before, its rollback only took effect at the next
  restart.

### For developers

- **`eph-config`:** the config model, parsing and every check, as a
  library. It builds the NAT, forwarding and overlay tables to catch
  errors, so anything that writes configs (a controller, say) checks them
  exactly as the router does. The enrolment string's parser is in it too.

### CI and releases

- Pull requests run the full CI (unit tests, fuzzing, the SD-WAN lab, the
  image build and its end-to-end test) before they're merged; merging no
  longer runs it again.
- A release tag now builds its own image with the real signing keys,
  tests it in full, and publishes exactly the image that passed. This
  release is the first built that way.

### Dependencies
- Added for the controller connection: `rustls` 0.23 on `ring` 0.17,
  `tokio-rustls`, `tokio-tungstenite` 0.24, `rcgen` 0.13,
  `rustls-webpki`, `ed25519-dalek` 2.2 and `time`. `cargo deny` now also
  allows the ISC licence (ring, rustls-webpki, untrusted), which is
  permissive like MIT.

### Documentation
- [The controller contract](https://github.com/mornev-sudo/ephemeris/blob/v0.13.0/docs/controller-api.md):
  principles, identity and enrolment (including zero-touch and claim
  tokens), the connection, config, telemetry, live tables (not built on
  the router yet), versioning and security.

### When upgrading
- **Nothing changes unless you enrol the router.** The connection to a
  controller only starts with a `[controller]` section (or an enrolment
  string handed over at deployment).
- **New files in `/var/lib/ephemeris`:** `controller-identity` (made at
  the first start), `config-version`, and while a confirmed commit waits,
  `pending-confirm.json`.
- **Confirmed commits that need a restart** now restart the router if
  they aren't confirmed in time, to go back to the config before.
- **A push from a controller discards** a config staged in the portal but
  not committed.
