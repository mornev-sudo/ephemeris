## Ephemeris 0.12.3

Updates without a management network. The router's own connections
(software updates, DNS, time) can now leave through the data plane, out of
the WAN like a LAN host's. A router with only a LAN and a WAN updates
itself. Routers no longer forward link-local addresses.

### The router's own traffic through the data plane

Until now the router's own connections could only use the management
port: Linux never sees the data-plane cards, and the internal link to the
data plane only carried SSH and portal traffic coming in on inside
interfaces. Now:

```toml
[management]
outbound = "dataplane"   # default: "management", as before
```

After `ephctl restart`:
- **The way out.** The router's own packets are routed like a LAN host's:
  a session, NAT to the outgoing interface's own address, out of a local
  interface. For downloads from the internet, that's the WAN the default
  route uses, with its DHCP, PPPoE or static address. NAT pools and rules
  don't apply, and SD-WAN tethers aren't used.
- **The way back.** Replies come back through the same session to the
  router. Nothing outside can start a connection to the router this way.
- **DNS.** The router's system resolver uses the DNS servers learned on
  the outside interfaces (DHCP leases, PPPoE), so the update server's name
  resolves without a management network.
- **Fallback.** If ephemerisd isn't running, Linux ignores the route
  through the data plane, and the management port's default route, if
  any, takes over.
- **The management port** then only reaches its own subnet. A management
  client behind another router can't reach SSH or the portal through it
  any more; reach them on an inside interface instead
  (`management = ["https", "ssh"]`).
- On the portal: Management, "Router's own traffic".

Guide: [chapter 10, "Which way the download goes"](https://github.com/mornev-sudo/ephemeris/blob/v0.12.3/docs/learn/10-ab-updates.md).

### Security

**Link-local addresses are never forwarded.** Packets with a source or
destination in 169.254.0.0/16 are dropped as `martian`, as RFC 3927
requires of routers. This also keeps the router's internal host-path
addresses unreachable from the network.

### Testing
- **End-to-end:** a new phase switches the test router to
  `outbound = "dataplane"`. Host B plays the update server. The test checks:
  - the default route through the data plane is in place;
  - the router pings host B, and downloads a file from it over HTTP;
  - host B sees the router's WAN address (NAT);
  - the router's DNS servers come from the WAN's DHCP lease;
  - management SSH keeps working.

  Then it switches back and checks the route is gone.
- **Unit tests:**
  - the router's own packets leave NAT'd out of the WAN, and the reply
    comes back to the router;
  - the rest of the connection follows its session;
  - nothing outside can start a connection or reach the router's address
    directly;
  - its own addresses, broadcasts, multicast and link-local are refused as
    destinations;
  - the link-local filter, and the new config setting.

### When upgrading
- **Nothing changes unless you set `outbound = "dataplane"`.**
- **Link-local traffic** (169.254.x.x, e.g. a device that failed to get a
  DHCP lease) is no longer forwarded between interfaces. It was never meant
  to leave its own network; such devices now only reach their own subnet.
